## Summary

Implemented the Terraform remote backend for all stacks using S3 with native locking (`use_lockfile = true`), as decided in ADR-0002 (Option B). The bootstrap was executed in three phases:

- **Phase 1**: Applied stack `00-remote-backend-stack-ai/` with local state to create the S3 bucket and all security controls.
- **Phase 2**: Added `backend "s3"` block to stack-00's `versions.tf` and migrated its own state into the newly created bucket.
- **Phase 3**: Added `backend "s3"` block to stack-01's `versions.tf` and migrated the existing networking stack state from local to S3.

## Design Decisions

### Bucket Naming: account_id + environment suffix

Bucket name follows the ADR pattern: `{prefix}-{account_id}-{environment}`. This guarantees global uniqueness (S3 bucket names are globally scoped) without collision risk across accounts or environments.

### `force_destroy = true` in dev only

The `dev.tfvars` sets `force_destroy = true` to allow teardown of the dev bucket if needed (e.g., end of workshop). `staging.tfvars` and `production.tfvars` set it to `false`. The `lifecycle { prevent_destroy = true }` guard on the resource provides a Terraform-level safeguard for all environments regardless of this flag.

### Lifecycle rule for `.tflock` files uses `expiration.days`, not `noncurrent_version_expiration`

Lock files are current objects (not versioned). `expiration { days = N }` correctly targets current object age. `noncurrent_version_expiration` would have no effect on them.

### `newer_noncurrent_versions = 5` retention floor

Added to the noncurrent version expiration rule to keep the 5 most recent non-current versions regardless of age. This provides a safety net for rapid sequential applies before the 90-day expiration window.

### `depends_on` explicit chain in s3.public-access-block.tf and s3.policy.tf

`block_public_policy` must be active before a bucket policy can be attached (AWS API returns an error otherwise). The `depends_on` chain `s3.tf -> s3.public-access-block.tf -> s3.policy.tf` enforces this ordering explicitly, supplementing Terraform's automatic dependency resolution via references.

### Terraform MCP validation performed pre-implementation

All 6 S3 resource types (`aws_s3_bucket`, `aws_s3_bucket_versioning`, `aws_s3_bucket_server_side_encryption_configuration`, `aws_s3_bucket_public_access_block`, `aws_s3_bucket_ownership_controls`, `aws_s3_bucket_lifecycle_configuration`, `aws_s3_bucket_policy`) validated against provider v6.46.0 via Terraform MCP before writing any HCL. Key finding confirmed: `bucket_key_enabled` is at the `rule` level in SSE config, not inside `apply_server_side_encryption_by_default`.

## Rollback Plan

### During bootstrap / pre-migration of other stacks (stack-00 only)

State is in S3 but no downstream stacks depend on it yet. Rollback steps:

1. Revert `00-remote-backend-stack-ai/versions.tf` to remove `backend "s3"` block.
2. Run `terraform init -migrate-state` to move state back to local (`terraform.tfstate.phase1-backup` is available as a source).
3. Set `force_destroy = true` in `envs/dev.tfvars` (already set), then run `terraform destroy -var-file="envs/dev.tfvars"`.

### After both stacks migrated (current state)

Both `stacks/00-remote-backend/terraform.tfstate` and `stacks/01-networking/terraform.tfstate` are in S3.

Do NOT destroy the bucket while stacks depend on it. To roll back the migration of stack-01:

```bash
cd 01-networking-stack-ai
# Pull current remote state to local file
terraform state pull > terraform.tfstate.recovered

# Revert versions.tf to remove backend "s3" block
# Then migrate back to local
terraform init -migrate-state -backend=false
```

To decommission the entire backend:
1. Migrate each downstream stack back to local state (as above).
2. Remove `backend "s3"` from `00-remote-backend-stack-ai/versions.tf` and run `terraform init -migrate-state`.
3. Set `force_destroy = true` and run `terraform destroy -var-file="envs/dev.tfvars"`.

### Lock-file orphan recovery (runbook RB-BACKEND-001)

If a Terraform process crashes and leaves a `.tflock` file:

```bash
# The LOCK_ID appears in the error message from `terraform plan/apply`
terraform force-unlock <LOCK_ID>
```

The lifecycle policy also automatically expires orphaned `.tflock` files after 7 days.
